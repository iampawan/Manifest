# v0.18.0 — dev-centric pickup flow (beta)

**TL;DR.** Most real-world PRDs live in JIRA / Google Docs / Slack /
Notion — not in Manifest. The PM writes one, hands it off, and walks
away. The dev does the rest. v0.18.0 ships a new entry point for that
case: `/contract pickup <source>`. The dev pastes any link or text;
the agent does the code archaeology and surfaces every gap in three
buckets you can act on in minutes.

Opt-in per repo. Existing flows unchanged. Tested as beta — see
"Known gaps" below.

---

## Why this release

The PM-authors-the-contract flow we shipped in 0.17 works when the PM
is in Cowork / Claude Code with you. In the real world, most PMs:

- Write PRDs in JIRA, Google Docs, Slack, Notion, or as a screenshot
  of slides.
- Don't know the code, the history, or the dependencies.
- Hand the PRD to a dev and move on to the next thing.

So the dev is the one who has to make the PRD build-ready — by reading
the code, grepping the archive, checking Slack for prior context,
finding past bugs on the same surface, and going back to the PM with
the *right* questions (without pinging them five times across the day).

Manifest 0.18 does that work *for* the dev. The PM stays in their
normal tool and never has to touch Manifest.

## What's new

### `/contract pickup <source>`

A new subcommand. Source is anything:

| You paste this | Agent reads via |
|---|---|
| `https://your-org.atlassian.net/browse/ENG-1234` | Atlassian MCP |
| `https://docs.google.com/document/d/...` | Google Drive MCP |
| `https://linear.app/...` | Linear MCP |
| `https://notion.so/...` | Notion MCP |
| `https://yourcorp.slack.com/archives/.../p...` | Slack MCP |
| `https://figma.com/file/...` | Figma MCP |
| Pasted text | direct |
| A dropped image | multimodal |

The agent fetches it, follows links inside it one level deep (Figma
inside JIRA, tech spec inside the Google Doc, the linked Notion
page), and pulls related history in the background — past contracts
on the same surface, postmortems, recent Sentry, open PRs touching
the same files.

Then it shows you one card with every gap sorted into three buckets.

### The three-bucket gap sorter

Every gap in the PRD lands in exactly one of:

- **A. Agent fills from code/history.** High-confidence proposals
  with a source. Things like "perfBudget = 50ms (stack default)",
  "event name = `filter_applied` (matches your event catalog)",
  "empty-state copy = reuse `i18n/search.no_results`", "AC for B3
  drafted from SC-088's combined-filter AC." Each one is a single
  tap to accept or edit.
- **B. Dev decides.** Engineering judgment the PM can't give. Things
  like "past contract SC-103 hit a memory leak in chip rendering —
  use the new pattern from SC-211 instead?", "search endpoint p95 is
  50ms; two filters will push past — add a cache layer?", "open PR
  #4421 also touches this path — coordinate?"
- **C. Only PM can answer.** Genuine product unknowns. Each is
  drafted as a PM-facing question scoped to a behavior, in plain
  language. You review the wording, edit if needed, hit send. All of
  them go out as **one batched JIRA comment / Slack reply / Notion
  comment** in your voice. PM answers in their tool. You move on.

### PM-channel question posting

Drafted Bucket C questions go to the PM via the channel the source
came from:

- JIRA ticket → JIRA comment on the same ticket
- Slack thread → reply in thread
- Notion → page comment
- Google Doc → suggestion comment

Posted in *your* voice, with your name on it. The PM sees a normal
message from the dev they handed work to. Optional `— <you> (via
Manifest)` footer for audit trail (`pickup.identifyAgent` in
`repos.yml`).

### Answer watcher

After you send, the agent watches the PM channel for replies.
Polling cadence: every 5 min for the first 2h, every 15 min for the
next 24h, hourly after that. When the PM answers:

1. Parses the answer per question.
2. Applies it as an AC edit (new AC, refined behavior description,
   or `outOfScope` add).
3. Drops a provenance comment: `<!-- From: Q-N · <PM> · <date> -->`
4. Moves the resolved question to a sidecar `<ID>.qa.md` log file.
5. Re-verifies incrementally on just the changed fragments.
6. Pings you with a one-line summary of what changed.

Implementation on non-blocking behaviors can run in parallel while
you wait. Default is non-blocking; you flag a question as blocking
if you genuinely can't start without the answer.

### `critic-code-context`

A new dev-side critic. Different from `critic-regression` (which
flags *risks*); this one proposes *answers*. It feeds the Bucket A
auto-fills and Bucket B dev-decides items by reading a precomputed
cache of:

- The event catalog and naming conventions in your code.
- All i18n keys.
- Stack defaults for perf budgets and required comms states.
- Similar past contracts on the same surface (especially archived
  rolled-back / partial ones — they're full of lessons).
- The dependency graph: shared modules, feature flags, A/B tests,
  endpoint budgets.
- Locale / device / segment branches the code already handles that
  the PRD might not address.

Every Bucket A proposal points to its source (a file path + line, or
a contract ID + fragment). Your trust is in the trace, not the
suggestion.

## How to try it

Pull v0.18.0 and turn pickup on for one repo first:

```yaml
# .manifest/repos.yml
pickup:
  enabled: true
  identifyAgent: true       # adds "(via Manifest)" footer to PM-facing posts
  defaultChannel: jira      # or: slack | notion | gdoc
  blockingByDefault: false  # questions are non-blocking unless you flag them
  cacheTTL: 24h             # codebase analysis cache lifetime
```

Then on a real JIRA ticket your PM assigned you:

```
/contract pickup https://your-org.atlassian.net/browse/ENG-1234
```

You'll see a card with the draft contract + the three-bucket gap
view in ~30 seconds. Tap through Bucket A, walk Bucket B, send
Bucket C to your PM in one click.

Without `pickup.enabled: true`, the command falls back to
`/contract new` with a notice. Nothing changes for repos that don't
opt in.

## When to use which entry point

| You're in this situation | Use |
|---|---|
| PM is in Cowork with you, writing the spec together | `/contract new` (unchanged) |
| PM wrote the spec elsewhere and handed it off | `/contract pickup <source>` *(new)* |
| Quick bug fix, no real spec | `/fix` (unchanged) |
| Already-promoted contract going through CI | unchanged: `@claude /implement`, `verify-pr`, etc. |

The pickup flow doesn't replace anything; it adds the missing entry
point for the case the rest of the pipeline assumed away.

## What also shipped (folded in mid-cycle)

Two pieces that started as "known gaps" made it into v0.18 itself:

- **`scripts/build-code-context.mjs`** — the cache builder for
  `critic-code-context`. Scans repos for event catalogs, i18n keys,
  flags, shared modules; indexes past contracts by surface; flags
  rolled-back / partial history. Output: `.manifest/.cache/code-context.json`.
  Sub-second lookups after the first build. Runnable locally OR on
  the nightly cron at `workflows/code-context-build.yml`.

- **`scripts/answer-watcher.mjs`** — polls PM channels for replies to
  open pickup-flow questions. Emits a JSON report the contract-pickup
  skill consumes in apply-mode. Runnable locally OR on the 15-minute
  cron at `workflows/answer-watch.yml`.

## Known gaps (still deferred)

These are listed so you know what to expect during beta testing:

- **Answer-watcher channel adapters return `mcp-unavailable` from a
  raw Node process.** They log what they would call when you pass
  `--verbose`. Production detection needs either (a) running from
  inside Claude Code / Cowork (the relevant MCP is available there)
  or (b) a thin REST proxy on the MCP host. The harness + report
  schema ship in v0.18; production wiring is the next patch. As a
  workaround: re-run `/contract pickup` after your PM replies — the
  skill picks up the new comment via MCP.
- **Cross-repo cache builder** reads from local clones via the
  `path:` field in `repos.yml`. Entries with only `github:` (no
  local clone) are skipped — pulling source via the GitHub MCP from
  the builder is a follow-up.
- **Slack message-link parsing** covers the common URL shape
  (`/archives/<channel>/p<timestamp>`). Exotic workspace URLs may
  need a follow-up.
- **PM-facing wording** is sometimes too jargony on first run. The
  skill instructs the agent to use plain language, but until you've
  picked up a few contracts on your team's vocabulary, *read the
  drafted message before sending*. Edit freely; the default text is
  a starting point, not final.

## Existing flows — unchanged

If you don't enable pickup, this is a no-op release. All v0.17.0
behavior is preserved:

- `/contract new`, `/contract verify`, `/contract fix`,
  `/contract promote`, `/contract decompose`, `/contract diagram`,
  `/contract migrate`, `/contract archive`
- `@claude /implement`, `@claude /fix-pr`
- `verify-pr.yml`, `verify-deploy.yml`, `rollback-guard.yml`,
  `launch-monitor.yml`
- `/fix`, `/status`, `/canary`, `/rollback-check`, `/postmortem`,
  `/launch`

No frontmatter changes to existing contracts. No new required
fields. No migration needed.

## Install / upgrade

If you installed via the marketplace:

```
/plugin install manifest@manifest
```

…will pull 0.18.0 once the tag is published.

If you're tracking a specific tag:

```
/plugin install manifest@v0.18.0
```

If you cloned for development, just `git pull` on `main` (after the
0.18.0 merge lands).

## Roadmap context

This release is the first piece of a broader vision laid out in
[ROADMAP.md](../../ROADMAP.md) — UGC Agents covering Development,
Customer Support, and Operations. Pickup is the dev-handoff piece of
the Development pillar. Next likely shipments:

- Cache builder for `critic-code-context` (turns first pickup from
  ~30s to sub-second).
- Cron-backed answer watcher (so you don't have to re-run pickup
  when PM answers).
- Post-launch tracking agent (4-week DM cadence after 100% rollout
  with quantitative + qualitative verdict).
- NTO ticket auto-debug for the Customer Support pillar.

## Credits + feedback

Tested as beta on a small set of repos before this release. If you
try pickup, the most useful feedback is:

- Which Bucket A proposals were wrong (so the cache schema can
  improve).
- Which PM-facing question wordings you had to rewrite (so the
  drafting prompts can improve).
- Which sources the fetcher tripped on (links it should have followed
  but didn't, formats it choked on).

Open an issue with `[pickup-beta]` in the title.
