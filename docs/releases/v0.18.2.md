# v0.18.2 — code quality hardening + dashboard-style PRs + plain-English comments

**TL;DR.** Cursor BugBot caught three bug classes on the first
Manifest-shipped voice-dictation PRs that `code-review` should have
caught itself. This patch closes them at the source. It also reshapes
the PR body into a dashboard a reviewer reads in 30 seconds and a
finding into a 10-second-readable block — both items you've been
asking for.

No migration. All additive.

---

## What was wrong

The first PRs Manifest shipped against the UWS-502 voice-dictation
contract had three Cursor-flagged issues across two repos:

1. **Contract self-contradiction** — B4 said both "only tap/Esc/blur
   ends the session" and "network/no-speech/aborted errors stop the
   session." A state-machine reader gets ambiguity; the implementer
   guessed wrong.
2. **Empty catch + side effects.** `try { recognition.start() } catch {}`
   followed by `setIsRecording(true)` + start-event analytics. The
   action could fail silently and the UI lies about success.
3. **`useState` race guard on rapid clicks.** Reading `isRecording` from
   state across two rapid clicks → second click sees stale guard,
   re-enters, zeros `insertedCharCount`.

All three were in `code-review`'s territory and should have been
flagged before the PR shipped to a human. This release adds the
patterns and a self-review pass that catches them before the first
push.

## What changed

### Spec layer — `critic-edge-cases` now checks internal consistency

Today's `critic-edge-cases` asks gap questions ("what happens if X").
It didn't ask "do the answers in the spec agree with each other."
That's the gap that landed the B4 contradiction.

New section in `skills/critic-edge-cases/SKILL.md`: **State-machine
consistency.** For every named transition (start / stop / end /
restart / error / timeout / teardown / etc.):

1. Enumerate every place that transition is mentioned in the
   contract.
2. Compare the statements.
3. Flag disagreements — blocker if the spec becomes genuinely
   undecidable, warning otherwise.
4. The suggestion must include the exact disambiguating language
   to add (not just "this contradicts itself").

Plus the "rapid double-action" finding (which existed but defaulted
to warning) is now escalated to blocker unless an AC or `outOfScope`
line names a concrete guard.

### Code layer — `code-review` got three high-recurrence patterns

Every Cursor BugBot finding from the test PRs maps to a pattern now
explicit in `skills/code-review/SKILL.md`:

- **Empty catch + side effects.** Any `catch (e) {}` / `catch {}`
  followed by state mutation / analytics / navigation that pretends
  the try block succeeded → blocker. Must re-throw, log + bail, or
  contain only genuinely side-effect-free logic.
- **`useState` as race guard.** Handler reading a React state value
  to decide "am I running?" races against batched re-renders → warning
  with `useRef` / `disabled` fix suggested.
- **No-op / silently-swallowed errors.** Caught errors that aren't
  re-thrown, reported to error tracking, or surfaced to the user →
  warning minimum; blocker when hiding user-visible state failure.
- Plus two adjacent patterns: analytics fired before the action
  succeeded (skews funnels), and state writes after unmount / dispose
  (memory bugs / warnings).

### Finding format — plain English, four parts, code snippet

`reference/PR-COMMENT-STYLE.md` is the new canonical style. Every
finding now renders in this shape:

> 🐛 **Race condition on rapid clicks**
>
> When the user clicks the mic button twice quickly, the second
> click runs before React has updated `isRecording`. The guard
> thinks the session is still off and fires again — resetting
> `insertedCharCount` to 0.
>
> **Why it matters.** Users who double-tap (common on mobile,
> common when impatient) will lose their dictation character count
> and may see weird state during the brief overlap.
>
> **The fix.** Use `useRef` for the "is it running" flag instead
> of `useState`. Refs update synchronously, so the second click
> sees the right value.
>
> ```ts
> // before
> const [isRecording, setIsRecording] = useState(false)
> // after
> const isRecordingRef = useRef(false)
> ```
>
> `voice-dictation-toolbar-button.tsx:42`

Same finding, before this release:

> CR-007: useState flag used as concurrency guard. The handler reads
> `isRecording` from state which is stale across rapid renders.
> Suggest `useRef`.

The output schema now requires `plainTitle`, `whatHappens`,
`whyItMatters`, `theFix`, `codeSnippet` fields. Legacy `message` and
`suggestion` are kept for tooling. Findings missing the new fields
are surfaced as critic bugs — the old terse format can't leak
through.

### Implementer — pre-write reconnaissance + pre-push self-review

Two structural changes in `skills/implement/SKILL.md`:

**Pre-write recon (now mandatory, step 3 in the skill):**
- `grep` for every symbol the plan says to create. If it exists, use
  it. Don't create `formatDate2` next to `formatDate`.
- Read 1–3 sibling files in the target folder. The plan says *what*
  to build; the sibling shows *how this team builds it*. Copy the
  structure.
- Consult `.manifest/.cache/code-context.json` — existing events,
  i18n keys, flags, shared modules, similar past contracts, rolled-
  back history. Use what's there; don't duplicate.
- Note the recon findings in the PR body — transparency for the
  reviewer.

**Pre-push self-review (step 7b, now mandatory):**
- Run the `code-review` critic on the diff *before* pushing.
- Max 2 in-place fix iterations to clear blockers.
- If anything remains, push with a self-review comment naming the
  open issues — don't churn.
- Catches the empty-catch / race / no-op-error class before CI does.

### PR body — dashboard, not a paragraph

The implementer's PR body now follows a required template
(in `skills/implement/SKILL.md` step 8):

```
## What this PR does
<2–3 sentences. Plain English. PM + new-engineer test.>

## Contract
<ID · title · sizing · SLA · AC count · link to revision>

## Shape of the change
<Mermaid diagram, either from the contract's Diagrams section or
generated for this PR. Required, not optional.>

## Files changed
<Table: file | one-liner of why it changed.>

## AC coverage
<Table: AC | what it checks | test file:line | ✅/❌>

## What I read before writing code
<The recon report — sibling files read, code-context cache used,
existing patterns followed.>

## Self-review summary
<Code-review critic findings the implementer caught and fixed
itself, plus any genuinely open issues.>

## How to test locally
<Exact commands + a manual path the reviewer can walk in a minute.>

## Risk callouts
<Where to look first if this breaks. Required section — write
'no risky areas' if true; don't skip it.>
```

A reviewer with 30 seconds knows what / why / what to scrutinize.
A reviewer with 5 minutes can merge without opening other tabs.

### The "Cursor never finds anything new" mechanism

The bigger structural fix in 0.18.2 is the bug-pattern catalog +
mandatory full-scan self-review. The problem we were solving:

> *Cursor catches issue A → dev fixes → Cursor catches B → dev
> fixes → Cursor catches C → ...* Each round wastes dev time.

The fix isn't smarter critics for "this PR." It's a catalog that
grows every time something slips through, and a self-review loop
that always scans the full catalog — so fixing pattern A doesn't
leave the agent ignorant of pattern B.

**`reference/BUG-PATTERNS.md`** is the catalog. Six entries seeded
from recent Cursor findings (BP-001 ... BP-006); intended to grow
one direction only. Every Cursor / human / postmortem finding that
wasn't already in the catalog becomes a permanent `BP-NNN`. The
implementer pre-empts the patterns at write time; the code-review
critic verifies at self-review time. Same source of truth.

**`reference/RECOMMENDED-LINT-RULES.md`** is the mechanical layer.
Most of the catalog patterns are catchable by the right ESLint /
Dart analyzer / golangci-lint / ruff rules at the right severity.
Document gives the exact configs per stack. Repos that adopt all of
them typically see Cursor findings per PR drop ~70% within a few
PRs — because the linter rejects the patterns at editor save time,
before the AI sees the diff.

**Self-review now re-scans the full catalog on every iteration.**
Previously the implementer's pre-push self-review fixed the round's
findings and pushed. The agent didn't know to look for the next
pattern in the catalog. Now: every iteration loads
`reference/BUG-PATTERNS.md` and checks every active pattern. By
iteration 2, the agent has scanned for every known shape. Round 3
either catches genuinely-new issues (which then become new BP
entries) or is empty.

The end state: external reviewers should find nothing new on a
given PR. When they do, the finding gets added to the catalog and
the next PR pre-empts it. Whack-a-mole becomes a ratchet.

### Self-review is tunable

Default is on. If your team measures and finds self-review eats
more than it saves on your diff sizes, dial it via `repos.yml`:

```yaml
implementer:
  selfReview: on             # default — always run
  # selfReview: off          # skip; CI / external reviewers
                             #   become first line of defense
  # selfReview: auto         # run only on diffs ≥ threshold
  selfReviewMinChangedLines: 0   # used only when "auto"
  selfReviewMaxIterations: 2
```

The math (per PR):

| Scenario | Before 0.18.2 | After (selfReview: on) | Delta |
|---|---|---|---|
| Clean PR, never any findings | ~5 min | ~9 min | **+4 min** (per run) |
| PR with 1 external-reviewer round | ~20 min | ~10 min | **-10 min** |
| PR with 3 external-reviewer rounds | ~45 min | ~12 min | **-33 min** |

Compute roughly 1.5–2× per PR (the critic runs once pre-push and
again in CI). The agent-time tradeoff is worth it for any team
where dev attention is more expensive than agent compute and where
PRs would otherwise take more than 1 iteration. If your PRs ship
clean on first push consistently, `selfReview: auto` with a
threshold (e.g. 30) keeps the cost only where the value is.

### Workflow — optional static-check block

`workflows/pr-verify.yml` now has a commented-out section with the
canonical lint / typecheck / test commands per stack (Node / Flutter /
Go). Repos relying on Manifest for CI can uncomment their block;
repos whose own CI already runs these can leave it off. The AI
critics run regardless — this just catches the mechanical issues
faster and cheaper.

## Upgrade

```
/plugin marketplace update manifest
/plugin install manifest@v0.18.2
```

No config changes. Existing contracts, repos.yml, and workflows
keep working unchanged. The next implementer run produces the new
PR body automatically; the next pickup run uses the consistency
check automatically.

## What this is NOT

- Not a fix to existing PRs already shipped (those got the old
  output — re-run `@claude /implement <ID>` or `@claude /fix-pr <ID>`
  to refresh).
- Not a change to the contract format. Existing contracts stay
  valid as-is.
- Not stack-aware static checks turned on by default — that's the
  uncommented block in the workflow; opt in if you want it.

---

## Why this is 0.18.2, not 0.18.1

0.18.1 fixed the *pickup* skill (the Spec entry). 0.18.2 fixes the
*implementer + reviewer* skills (the Build phase). Different code
paths, different bugs, different test PRs. The motivating Cursor
findings landed in the implementer's output and should never have
reached the reviewer in their original form.

## Try the difference

Re-run the implementer on a contract you've shipped recently. You
should see:

1. The PR body opens with a Mermaid diagram of the change, not a
   prose paragraph.
2. The body has a "What I read before writing code" section listing
   the sibling files and code-context entries consulted.
3. The body has a "Self-review summary" showing what the
   implementer caught and fixed before pushing.
4. Any `code-review` comments use the plain-English four-part
   format — title with emoji, what-happens, why-it-matters,
   the-fix with snippet, file:line.
5. If you put a contract through pickup with a self-contradiction
   (e.g., two clauses about the same state transition disagreeing),
   the verify step flags it as a blocker with the specific
   disambiguating language to add.
